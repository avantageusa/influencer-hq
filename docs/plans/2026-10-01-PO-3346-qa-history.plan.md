## Problem

PO-3330's last unimplemented AC item:

> Given I have asked questions during a session
> When I leave and return later
> Then my progress resumes as before and the previous exchanges are available

Scope was ambiguous before this: "available" could mean just a read-only
display of past Q&A, or it could mean Ask Sami stays fully interactive
(implying a live Gary session gets reopened automatically on every resume).
The latter is a materially bigger piece — none of PO-3102's resume paths
currently reopen a live session at all (`start()`/`openGarySession()` only
run for a genuinely fresh arrival), and doing so on every resume means
deciding whether that ties up a fresh avatar seat each time (Gary's own
guidance elsewhere is that every video session does).

Posted the planned scoping (read-only, no live session reopen) to Ivan
Vladić directly, who confirmed "Yes" on 2026-10-01. Scope is locked:
persist and redisplay past exchanges, don't touch session-reopening
behavior at all.

## Approach

- `inc/aicoach-progress.php` — added `qaHistory` to
  `ihq_aicoach_progress_sanitize_partial()`, same whitelist-and-cap
  discipline as every other field here (`identity`/`channels`/etc). New,
  larger cap (`IHQ_AICOACH_PROGRESS_MAX_QA_TEXT_LENGTH = 1000`) separate
  from the existing `IHQ_AICOACH_PROGRESS_MAX_FIELD_LENGTH` (190, sized for
  short form fields) — spoken Q&A text runs a full sentence or more.
  `IHQ_AICOACH_PROGRESS_MAX_QA_HISTORY = 20` caps the array itself.
- `js/aicoach-coach-flow.js` —
  - `qaHistory` (array, newest last) tracked inside `buildAskSami()`,
    rendered into a new `.aicoach-ask-history` element sitting above the
    existing live `answerEl` (which keeps behaving exactly as it already
    did for the current in-flight answer — untouched).
  - `askQuestion()`'s success path pushes the just-answered pair, re-renders,
    and calls `saveProgress({ qaHistory })` — before
    `speakAnswerOrFallback()`, not after, so a slow/failed spoken-answer
    step can't risk losing a Q&A pair that already succeeded.
  - `applyResumedQaHistory()`, exposed the same way
    `applyResumedIdentity()`/`applyResumedChannels()` already are, called
    from `init()` right alongside them. Deliberately does NOT touch
    `garySessionId`/`qaClientReady`/`askSamiBtn.disabled` — Ask Sami becomes
    askable again only the same way it already does on any resume (once the
    flow reaches a point that opens a session), per the locked scope.
- `page-home-aicoach.php` — CSS for `.aicoach-ask-history` (scrollable,
  height-capped so a long history can't push `.aicoach-ask-panel` past what
  its anchored positioning can gracefully handle) and its item/question/
  answer children, matching the panel's existing color/spacing conventions.
- `tests/aicoach-progress.test.php` (new — this file had no test coverage
  before) — the sanitizer's qaHistory branch: valid entries round-trip,
  malformed entries are dropped without a fatal, oversized text is capped
  not rejected, an oversized array keeps the most recent entries, and a
  real `save()`/`load()` round-trip confirms the merge behavior (a later
  qaHistory-only save doesn't clobber an earlier `tier` save, and a
  subsequent save with a longer array replaces the whole key rather than
  appending — matching how `channels` already behaves, since the frontend
  always sends its own full, already-capped array).

## Verified

- `php -l` / `node --check` clean on all four touched files.
- `php tests/aicoach-progress.test.php` — all checks pass.
- Live on wp-env: POSTed a real `qaHistory` through the actual REST route
  (`/wp-json/ihq/v1/aicoach/progress`, same nonce the real frontend uses),
  reloaded the page, confirmed `.aicoach-ask-history` rendered both resumed
  pairs correctly (question/answer text, 2 items, panel not forced open).
  Did not live-test the "ask a new question this same session, it gets
  appended" path end to end — this sandboxed environment has no real
  microphone, same caveat as every other PO-3346 PR's voice-input path;
  the code path is identical to the already-tested resume-render path
  (same `renderQaHistory()` call) plus a `saveProgress()` call whose
  sanitizer branch is covered by the new test.

## Blast radius

Additive only. `answerEl`'s existing behavior (the live "current answer"
display, its aria-live announcement) is untouched. `qaHistory` is a new key
in the progress record; nothing reads it except the new display code, and
nothing existing writes to it. No change to session-opening/resume-stage
logic at all, per the locked scope.
